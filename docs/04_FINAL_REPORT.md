## 2. Что именно я проверил и как

### Миграция реальных данных — VERIFIED

Копия вашей папки `%APPDATA%\TelegramCenter` прогнана через миграцию.
**Оригинал не тронут** — я работал только с копией, и это проверено отдельно
после всех работ: `settings.json` там до сих пор без `schema_version`, то есть
формат v1, а обе сессии на месте и той же длины.

Миграция нашла ровно те три дефекта, которые я описал в аудите:

* правило `rule_d78e5c83e2c4` содержит `@operator`, оператора нет → правило
  перенесено, но **выключено**;
* оператор `op_0e05b3ec6bcf` ссылался на несуществующий файл сессии → остался
  как ник, отметка «авторизован» снята;
* две кампании ссылались на удалённый `acc_8697f5cf76ac` → **не удалены**,
  помечены ошибкой «аккаунт кампании не найден».

Текст шаблона `«Привет, как твои дела?»` скопирован в обе кампании снимком.
`bindings.json` и `health.json` переименованы в `.removed`, не удалены.
Перед миграцией снимается копия `data\` → `data.v1.bak\`.

16 тестов на миграцию воспроизводят точные формы ваших файлов.

### Каскад зависимостей — VERIFIED

Проверено и тестами, и вживую в браузере. В `%APPDATA%`-копии я вручную
поставил API-профилю `raw_state=ERROR` — оба аккаунта немедленно стали ERROR,
а их кампании заблокированы, хотя ни одна строка не пересчитывалась вручную.

Отдельный тест пишет в JSON заведомо противоречивое состояние — кампания
`RUNNING` на аккаунте с мёртвым прокси — и проверяет, что интерфейс всё равно
показывает ERROR, а планировщик отказывается запускать. Комбинация из §5
недостижима потому, что effective-статус не хранится, а вычисляется.

Тест `test_effective_state_is_never_persisted` читает сам JSON и убеждается,
что слов `effective` и `issues` там нет.

### `@operator` — VERIFIED

11 тестов, по одному на каждую из пяти точек и на обход:

1. создание правила с `@operator` без оператора — отклонено;
2. правка чистого правила в «плохое» — отклонено;
3. включение конфигурации с таким правилом — отклонено, флаг не применён
   наполовину;
4. отвязка оператора — правила с `@operator` выключаются, остальные не
   трогаются; удаление оператора делает то же самое для всех его аккаунтов;
5. **оператор исчезает во время задержки** — сообщение не уходит вообще.

Плюс проверка подстановки: `@operator` → `@supporthero`, и что в итоговом
тексте буквального `@operator` не остаётся. Совпадение регистронезависимое.

Всё это — с подставным Telegram-слоем: проверено, что отправки **не
происходит**, а не что она происходит правильно.

### Кампании — VERIFIED (логика), NOT VERIFIED (реальная отправка)

21 тест: арифметика трёх режимов расписания, снимок текста шаблона,
синхронизация результатов с списком каналов.

Сценарий обрыва: на втором из четырёх каналов API-профиль ломается прямо
во время прогона. Проверено, что отправок ровно две, кампания уходит в
PAUSED, два дошедших канала — SENT, два незатронутых — **PENDING, а не
FAILED** (их никто не пробовал, это не их ошибка).

Сценарий повтора: канал падает, помечается FAILED; на следующем запуске
повторяется только он, счётчик попыток растёт.

Пауза между каналами: подменённый `asyncio.sleep` показывает, что пауз ровно
на одну меньше, чем каналов, и все внутри заданного диапазона.

### Автоответы — VERIFIED (логика), NOT VERIFIED (реальные входящие)

22 теста. Приоритет FAQ над приветствием; «первое сообщение» срабатывает
один раз на собеседника; периодический выжидает окно задержки; несколько
совпавших FAQ-правил выбираются случайно, так что ни одно не монополизирует.

Живая связь с общим автоответом: меняем общий — у наследующего аккаунта
меняется сразу, без копирования.

Лимит FAQ: 3 правила при лимите 2 отклоняются; лимит 0 запрещает любые FAQ.

Обработчики входящих: `refresh()` вызван четыре раза подряд — обработчик
остаётся ровно один. Это тот самый баг «одно сообщение — N автоответов».

### Безопасность локального API — VERIFIED

21 тест: без токена 403, с чужим токеном 403, с чужим `Origin` 403, со своим
200, preflight `OPTIONS` отклоняется, мутирующие маршруты недоступны через
GET, токен разный при каждом запуске и не короче 32 символов.

Обход пути проверен сырым сокетом в трёх вариантах (`../`, `%2e%2e%2f`,
`....//`) — исходники не утекают.

Отдельно: медленный подписчик SSE не может застопорить публикацию — очередь
переполняется и теряет старые события, а не блокирует планировщик.

`build.bat`: `npm ci` → `npm run build` → `pytest` → PyInstaller. Падение

### Правки после первого прогона — VERIFIED

Семь замечаний по итогам живого использования:

1. **Наследование автоответа.** Аккаунт с пустыми полями снова использует общий
   шаблон: пустой набор правил больше не сохраняется как «свой пустой», а
   возвращает аккаунт к наследованию. Свой автоответ появляется в момент, когда
   добавлено хотя бы одно правило.
2. **Пустая FAQ-строка исчезает сама** — при уходе фокуса, с анимацией
   схлопывания; нижние строки сдвигаются вверх. Переход между двумя полями
   одной строки удаление не запускает.
3. **Переключатель своего автоответа в настройках аккаунта.** Первое правило
   приходит уже включённым; дальше состояние переключателя — выбор
   пользователя, и последующие правки его не переустанавливают. У аккаунта на
   общем автоответе переключатель неактивен с подсказкой, что делать.
4. **Выравнивание таблиц.** Заголовок колонки не получал её класс, поэтому
   «Отправлено» стояло слева над числами, выровненными вправо. Теперь заголовок
   наследует выравнивание колонки.
5. **Счётчик отправленных.** Повторяющаяся кампания перед новым циклом сбрасывала
   результаты по каналам, и счётчик показывал 0 при десятках реально
   отправленных сообщений. Добавлен накопительный `sent_total`, который не
   обнуляется между циклами. Для ежедневных и интервальных кампаний в таблице
   теперь просто число, без «0/1» — доля от одного прохода для них бессмысленна.
   Статус «Запланирована» между запусками — не ошибка: кампания действительно
   ждёт следующего срока.
6. **Автоответ не отвечает на флуд.** На каждый тип ответа для собеседника может
   быть только один ответ «в пути»: 25 подряд «привет» дают один ответ, а не 25.
   Как только ответ ушёл, следующее сообщение снова заработает ровно один.
   Защита снимается и при ошибке отправки, чтобы не заклинить.
7. **Один экземпляр на компьютер.** Именованный мьютекс: повторный запуск exe
   завершается сразу и ничего не делает. Проверено на собранном exe — второй
   запуск вышел с кодом 0, окно трея осталось одно, lock-файл продолжал
   указывать на первый процесс, а после «Завершить» приложение запускается
   заново без остатков.

### Значок в трее — VERIFIED

Приложение живёт в области уведомлений, окна нет. Меню — два пункта с
намеренно разными словами, чтобы «закрыть вкладку» и «остановить программу»
нельзя было спутать: **Открыть / Завершить**, в английском — **Open / Shut
Down**. Язык читается при каждом открытии меню, так что переключение в
настройках применяется сразу, без перезапуска. Иконка — ваш `icon.ico`,
отдаётся Windows как есть.

Сделано на `Shell_NotifyIcon` через `ctypes`, без `pystray`: тот потянул бы
Pillow — несколько мегабайт библиотеки для меню из двух пунктов. Размер exe
не изменился.

Проверено на запущенном приложении и на собранном exe: окно трея создаётся и
остаётся скрытым, принадлежит нужному процессу, API отвечает, а выход по
«Завершить» гасит HTTP, планировщик и Telegram-loop и убирает lock-файл.
13 тестов, среди них — реальная регистрация иконки в области уведомлений и
её снятие. Сам значок глазами я не увидел: экран был занят полноэкранным
приложением.

По ходу нашёлся баг: при повторном создании трея в одном процессе класс окна
оставался зарегистрированным и указывал на уже собранный сборщиком мусора
callback — следующий клик ронял процесс. Теперь класс снимается при выходе и
перерегистрируется, если остался от прошлого экземпляра.

### Завершение работы — VERIFIED

Последовательность выхода (`web.stop()` → `services.shutdown()` →
`telegram.shutdown()`) прогнана тестами: HTTP-поток умирает, порт
освобождается, висящий SSE-читатель отпускается, повторная очистка lock-файла
не падает. Сам клик по крестику Tk я не автоматизировал — выполняется ровно
этот код.

## 3. Что НЕ проверено вживую

Отдельно и прямо, как требует §42: **я не подключался к Telegram**. Ни разу.

Не проверено на настоящем Telegram:

* вход по телефону, по QR-коду, по токену бота;
* отправка сообщений в реальные каналы;
* срабатывание автоответа на реальное входящее сообщение;
* работа через реальный SOCKS/HTTP-прокси;
* проба API-профиля (она делает настоящий `connect()`);
* просмотр и отправка в чатах оператора;
* поведение при FloodWait, при ограничении аккаунта, при отзыве сессии;
* стабильность за сутки и поведение на десятках аккаунтов.

Что это значит на практике: код авторизации перенесён из Telesender
**дословно** и раньше работал, но я не могу заявить, что после переезда на
веб-машину состояний он по-прежнему работает, — это надо проверить руками.
Первое, что стоит сделать: войти одним аккаунтом и отправить одно сообщение
в один тестовый канал.

## 4. Известные ограничения

1. **Один экземпляр.** `instance.json` пишется, но повторный запуск exe
   поднимет второй сервер на другом порту, а не откроет вкладку у первого.
   Обнаружение живого процесса не реализовано.
2. **Периодический автоответ** трактован как «не чаще одного раза за окно
   задержки на собеседника». Если имелось в виду другое — правится в одном
   методе `_periodic_due`.
3. **Расписание DAILY** считает по локальному времени машины, без учёта
   перевода часов.
4. **Задержка автоответа не переживает перезапуск.** Если приложение
   закрыть, пока ответ ждёт своей задержки, он не будет отправлен.
5. **История сообщений не хранится.** Чаты оператора читаются напрямую из
   Telegram при открытии — это осознанно, чтобы не строить CRM.
6. **QR-код** рисуется из матрицы, посчитанной на бэкенде, и никуда не
   уходит. Внешних сервисов для этого нет намеренно: ссылка входа — это
   учётные данные.
7. **`data.v1.bak`** остаётся на диске после миграции. Удалять вручную,
   когда убедитесь, что всё перенеслось.
